## Story

**As a** developer maintaining RH Cursos payments,  
**I want** a documented and tested mapping between legacy course records and the `courses` payment model,  
**so that** checkout cannot drift between public catalog data and payment charge creation.

## Acceptance Criteria

1. The implementation identifies every live path that maps legacy `curso`/`turma` data to `courses.id` for payment creation.
2. A single server-side helper or clearly documented boundary owns course identity resolution for payment flows.
3. Payment creation still derives amount from `courses.preco` and never from client input.
4. Failure cases for missing or mismatched course identity return controlled errors.
5. Tests cover slug resolution, valid direct `courses.id` resolution, legacy id rejection, and missing course behavior.
6. Documentation notes the remaining dual-schema risk and the migration path if schema unification is deferred.

### CodeRabbit Focus Areas

- Course identity resolution must stay server-side; no client input can determine which `courses.id` is charged.
- Amount must remain derived from `courses.preco` and never accepted from client input, regardless of which course identity path is used.
- Legacy `curso`/`turma` identifiers must not be silently coerced into `courses.id` values; mismatches must be rejected, not guessed.
- Missing or mismatched course identity must return controlled errors without leaking internal schema or query details.
- Any new resolver code must not introduce a second, divergent source of truth for course identity.

## Story

**As a** buyer checking payment progress,  
**I want** payment status lookups limited to authorized checkout context,  
**so that** payment state is not disclosed by possession of a charge id alone.

## Acceptance Criteria

1. `/api/payments/status/[chargeId]` requires a signed lookup token or equivalent authorization mechanism.
2. A request with only `chargeId` cannot retrieve status.
3. Invalid, expired, or mismatched authorization returns a generic safe error.
4. Tests cover valid token, missing token, invalid token, mismatched charge id, expired token, and unknown charge.
5. If service-role remains necessary, its use is constrained and documented.

#### 7 Quality Checks

1. **Code review** — PASS. HMAC SHA-256 (`status-token.ts:43`); `timingSafeEqual` constant-time comparison (`:54`); signature verified before payload decode; payload binds `chargeId`/`purpose`/`iat`/`exp`; `server-only` import. Secret loaded via `PAYMENT_STATUS_TOKEN_SECRET` and validated at checkout before side effects.
2. **Unit tests** — PASS. Full authorization matrix covered.
3. **Acceptance criteria** — PASS (all 5).
4. **No regressions** — PASS. Full suite green (147/147 this session).
5. **Performance** — PASS. HMAC verify is cheap; token check short-circuits before DB.
6. **Security** — PASS. Strong design: constant-time compare prevents signature timing oracle; mismatch binding prevents token reuse across charges; 30-min TTL + 30s skew; generic error prevents enumeration. No new attack surface vs. prior open lookup — this *closes* one.
7. **Documentation** — PASS. `.env.example` updated with the new secret; inline rationale present.

#### Non-blocking Observations (low)

- **SEC-OBS-001 (low):** Token travels in the URL `?token=` form, which can land in proxy/access logs. The `Authorization: Bearer` path avoids this. Non-blocking given 30-min TTL and status-only response; prefer the header form for any server-to-server caller.

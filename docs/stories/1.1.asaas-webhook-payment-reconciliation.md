## Story

**As an** RH Cursos operations/admin user,  
**I want** Asaas payment webhooks to be received, authenticated, deduplicated, and reconciled into the local payment records,  
**so that** Pix/Boleto payment status in Supabase reflects Asaas status changes without manual reconciliation.

## Acceptance Criteria

1. A server-only Next.js route handler exists for Asaas webhook delivery under `src/app/api/` and accepts `POST` requests.
2. The route rejects unauthenticated webhook requests using `ASAAS_WEBHOOK_AUTH_TOKEN` from `getAsaasEnv()` and returns a non-2xx status without writing to Supabase.
3. A valid Asaas payment event writes one audit row to `payment_events` with the Asaas event id, Asaas charge id, event type, raw payload, and correlated local `payments.id` when the charge exists.
4. Webhook redelivery is idempotent: duplicate Asaas event ids do not create duplicate `payment_events` rows and do not re-apply payment status side effects.
5. When the webhook charge id matches `payments.asaas_charge_id`, the corresponding `payments.status` is updated to the payment status supplied by Asaas.
6. Unknown charge ids are still recorded in `payment_events` for audit with no local `payment_id`, and the route returns a successful response so Asaas does not retry indefinitely.
7. Invalid or unsupported payloads return a controlled JSON error response and do not throw unhandled server errors.
8. Unit tests cover authenticated success, missing/invalid auth, duplicate event handling, known-charge status update, unknown-charge audit logging, and malformed payload behavior.
9. Existing payment creation safeguards remain unchanged: checkout still derives amount from `courses.preco`, does not trust client amount, and does not introduce card data handling.

## Dev Notes

### Architecture Context

- The app is Next.js 16.2.9 App Router on React 19.2.4 and is deployed to Cloudflare Workers via OpenNext, not static Pages or Vercel. [Source: `docs/architecture/system-architecture.md#Actual Tech Stack`]
- The app uses Server Components, Server Actions, and route handlers for server-side behavior. Existing payment status route lives at `src/app/api/payments/status/[chargeId]/route.ts`. [Source: `docs/architecture/system-architecture.md#High Level Architecture`]
- Asaas charge creation is server-only in `src/app/actions/payment.ts` and `src/lib/asaas/*`. [Source: `docs/architecture/system-architecture.md#Payments`]
- The client-supplied payment amount is intentionally ignored; amount is derived from `courses.preco` and persisted into `payments.amount_cents` and `payments.course_preco_snapshot`. This invariant must not change. [Source: `docs/architecture/system-architecture.md#Payments`]
- `ASAAS_WEBHOOK_AUTH_TOKEN` is already required by `getAsaasEnv()`, but the architecture discovery found no webhook route. [Source: `docs/architecture/system-architecture.md#Current Technical Debt and Known Issues`]
- Payments use `payments` and `payment_events`; `payment_events.asaas_event_id` is unique and is the deduplication key for at-least-once Asaas webhook delivery. [Source: `supabase/migrations/20260617120000_payments.sql`]
- RLS is enabled for payment tables and public writes are intentionally absent; webhook writes should stay server-side via `createAdminClient()`. [Source: `supabase/migrations/20260617120000_payments.sql`]

- Hardened webhook token comparison with `crypto.timingSafeEqual` (length short-circuit before the byte comparison, since byte length is not secret), per QA FIX 4.
- Added a same-length wrong-token test to exercise the `timingSafeEqual` byte-comparison path (not just the length short-circuit).
- RPC now returns the currently persisted payment status so the webhook ACK does not echo stale or unknown payload status as if it had been applied.
